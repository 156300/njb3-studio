# 目标 2b/3：易驱线直拷、通用分区固件、USB3.0 的可行性论证

> 这一节给出**为什么做不到**以及**能做到的替代方案**。所有判断区分「证据」「静态推断」「物理定律」。

---

## 一、易驱线直读：能读到盘，但读不到"歌"

### 1. 易驱线能看到什么
NJB3 内置的是标准 **2.5 英寸 IDE/PATA 硬盘**（拆机图证据）。用 USB-IDE 易驱线把它接到 Win11，Windows 会把它当**块设备**识别（磁盘管理里出现一块未初始化/RAW 的盘）。到这一步是正常的——硬件层通用。

### 2. 为什么资源管理器里"没有歌"
- **证据 1（原厂手册第 4-9 节）**：File Manager 传进去的 MP3 是"数据文件"，明确 "cannot be played by your player"。
- **证据 2（libnjb HACKING）**：可播放曲目存在于**数据库**中，是"元数据字段 + 音频 BLOB"的记录，不是文件系统里的 .mp3 文件。
- **静态推断**：盘上的私有分区对 Windows 而言是未知文件系统，因此 `diskmgmt` 显示"未分配/RAW"、资源管理器无法浏览，**这是设计如此，不是驱动坏了**。

### 3. 能做到什么（安全、只读）
`scripts/disk_probe.py` 提供：
- 只读打开易驱线磁盘（`\\.\PhysicalDriveN`）或磁盘镜像文件（**绝不写入**）
- 解析 MBR/GPT 分区表，标出分区类型与偏移
- 全盘/分区扫描 `ID3` 标签与 MP3 帧同步字，定位音频数据并**提取副本**到指定目录
- 输出 JSON 报告（分区布局、发现的文件/标签、可疑数据库区域）

用途：**数据抢救、备份、迁移、取证**。如果机器坏了，这是把歌拿出来的最佳手段。

### 4. 做不到什么（写回让机器识别）
要让机器"认识"易驱线拷入的歌，必须**在私有数据库里插入记录**（含 artist/title/时长/文件映射等），而这需要：
1. 完整逆向盘上数据库的二进制格式（无公开规范、无写入工具）；
2. 精确维护 BLOB 与记录的映射、簇分配、校验——任何偏差可能导致开机 "Rebuilding Library" 失败或变砖。

libnjb 项目明确选择**不做**内核文件系统，也不直接写盘，原因就是写入必须重建元数据。因此"易驱线拷歌→机器直接识别"在缺乏私有格式规范的前提下**不可行**。

## 二、通用分区格式固件：不可行

用户的设想："做新固件让播放器支持通用分区（如 FAT32），资源管理器直接放歌，还能用 m3u。"

技术上需要同时满足三点，逐条看：

| 需要 | 现实 | 判定 |
|---|---|---|
| 固件源码/SDK 可改 | 固件以 `JB3Upgrade_*.exe` 自解压包分发，内部为打包/加密的 ARM 二进制，无源码、无符号表、无头文件、无编译工具链 | ❌ |
| 替换文件系统/数据库层 | 设备的播放逻辑深度依赖"数据库语义"（按 artist/album/genre 浏览、播放列表、SmartVolume）。改成 FAT 目录枚举等于重写整个上层应用 | ❌（工程量≈重写 OS） |
| m3u 直接被机器读取 | 固件需新增 m3u 解析器 + 路径到 BLOB 的映射逻辑，同样要改 OS | ❌ |

**不是"打补丁"能解决的，是重做一套嵌入式 OS + 应用。** 社区里 njbfs（Linux 内核 FS）曾尝试过文件系统桥接，但停留在 Alpha 且 2013 年后停止——佐证这条路的成本与风险。

**结论**：目标 2b 在"自制固件"层面不可实现。已证实的合法替代是：**用 PDE 协议软件把文件夹/m3u 映射写进设备数据库**（本方案路线 B 已实现），从用户视角达到"按文件夹/播放列表组织歌曲"的效果。

## 三、USB1.1 → USB3.0：物理上不可行

### 1. 速率由硬件 PHY 决定，固件改不了
- USB 1.1（12 Mbps）与 USB 3.0（5 Gbps）是**不同代际的物理层**：不同的收发器（PHY）、编码（NRZI vs 8b/10b）、线对数量、协议栈、控制器。
- NJB3 的 USB 控制器集成在 **EP7212 SoC** 内（该芯片数据手册随附于 `pdf/EP7212.PDF`），是 2002 年的 USB 1.1 Device 控制器。**固件运行在芯片上，不可能让同一块硅片跑 5Gbps**——就像不能靠升级软件让网线变成光纤。
- "增加电路模块使其支持 USB3.0"意味着重做主板：换带 USB3.0 Device 的主控、重新设计供电/时钟/固件栈、重写全部驱动与应用。这已不是改造 NJB3，而是一台新设备。

**判定：❌ 物理定律层面不可行，不是工程难度问题。**

### 2. 真正可行的提速路径（按推荐度排序）

| 方案 | 速率 | 说明 |
|---|---|---|
| **1394 火线（SB1394）** | 400 Mbps（约 30× USB1.1） | 机身自带接口！原厂手册称其为"fast data transfers"通道。需要一个 IEEE-1394 卡（TI 芯片组）并装老驱动；Win11 兼容性需实测，可能要在 XP 虚拟机里传 |
| **易驱线直读 IDE 硬盘** | USB3.0（5 Gbps，受硬盘本身限制） | 拆机取盘 → USB3.0-IDE 易驱线 → 全速镜像/取歌。配合 `disk_probe.py` 做备份与提取。**写回数据库仍受限**（见第一节），但"把歌拿出来"是最快的 |
| **XP 虚拟机 + 1394/USB 直通** | 取决于通道 | 素材里的 `vmos winxp` 可用于运行只能用 XP 的老工具；VMware 可做 USB 设备直通 |
| 保持 USB1.1 + 批量传歌 | 12 Mbps | 慢但稳定；`njb3_transfer.py` 的批量+断点重试可减少人工等待 |

### 3. 务实建议
1. 日常传歌：USB1.1 + 批量工具（可接受，歌传一次就好）。
2. 一次性导入大批量曲库：优先 1394；没有 1394 卡就用易驱线读盘 + 由 PDE 方式导入，或干脆在 XP 虚拟机里用原厂 CMS5 跑。
3. 数据抢救：易驱线 + `disk_probe.py`。
4. 忘记"USB3.0 固件改造"——那不是软件问题。

## 四、风险提示
- 拆机/换盘/易驱线操作有**物理损坏**风险；先在备份镜像上练习。
- 任何"写盘/刷机"操作前先做全盘镜像（可用 `disk_probe.py --image` 生成）。
- 固件升级不可回退（Readme 原文："This firmware upgrade is permanent. You cannot revert"），只在必要时刷官方版本。
- 关闭驱动签名强制/HVCI 会降低系统防护，操作完请恢复。
