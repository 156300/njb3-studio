## 1. libnjb：你说的链接确实不对

### 1.1 我们 README 里那个是死链

`README.md` 第 118 行和 `THIRD_PARTY.md` 第 19 行写的是：

```
https://github.com/libnjb/libnjb
```

实测返回 **404 — Page not found**，GitHub 上根本没有这个仓库。这是当初写文档时凭印象推断的路径，**需要更正**。

### 1.2 你给的两个链接才是对的

- **主站**：`https://libnjb.sourceforge.net/index.html`（可用）
  - 首页内容：支持设备清单（NOMAD Jukebox 1/2/3、Zen 系列、Dell DJ 等）、API 说明、支持的平台。
  - 明确写明协议叫 **PDE（Portable Digital Entertainment）**——这正是我们项目用的协议名。
  - 明确写明库本身不需要内核驱动，依赖用户态 **libusb**，Windows 下用 libusb-win32。
  - 页面最后修订时间停留在 **2005-03-03**，是老站。
- **源码/项目页**：`https://sourceforge.net/projects/libnjb/`（可用）
  - 项目全名：Creative NOMAD/Zen/Dell DJ API
  - 许可证：**BSD**
  - 注册时间 2001-07-31，最后更新 **2013-04-15**
  - 开发者：mechalas、snirkel
  - 说明：提供用户态 C 库，在 Linux/*BSD/Windows 上通过 PDE 协议与 Creative NOMAD/Dell DJ 通信。
- **版本目录**：`https://sourceforge.net/projects/libnjb/files/libnjb/`（可用）
  - 全部版本：1.0.1 → 1.1 → 1.2 → 2.0 → 2.1.1/2.1.2 → 2.2 → 2.2.1~2.2.7
  - **2.2.7（2011-06-25）是最终版，14 个版本中最新**，之后没有再发版。
  - 我们文档里写的 2.2.7 是对的。

> 补充：SourceForge 对脚本化直连返回 403（Cloudflare 防抓），但浏览器正常打开，链接本身有效。

### 1.3 我们最初从哪里拿到协议资料

项目里**没有保存 libnjb 源码副本**（发布目录刻意不含第三方源码）。根据开发记录的文字证据：

- `docs/01_硬件与协议分析.md` 第 55 行记录：**"libnjb 官方 HACKING（Debian sources `libnjb/2.2.5/HACKING`）"** —— 救援模式、硬盘维护菜单那部分来自 Debian 源码包的 2.2.5 版 HACKING 文档。
- `docs/USB接口指令清单.md` 第 8 行、以及 `agent.md` 几十处引用记录：**协议实现细节以 `libnjb 2.2.7 的 src/protocol3.c / protocol3.h` 为准**（命令号、帧 ID、状态字、playlist 结算规则、`njb3_get_track_tags[]`、`njb3_current_track()` 注释等）。

也就是说：**协议参照的是 2.2.7 源码，HACKING 背景资料来自 2.2.5 的 Debian 源码包**。当初具体是从哪个 URL 下载的源码包，开发记录里没有留下链接——这正是不该凭记忆写 GitHub 链接的原因，本报告把它固化下来。

### 1.4 perlnjb 是什么

`https://sourceforge.net/projects/libnjb/files/perlnjb/`（可用）：

- 只有一个版本 **0.1（2006-12-03）**，此后无更新。
- 从 SourceForge 项目页的编程语言分类可以看出 libnjb 项目同时涉及 **C 和 Perl**，perlnjb 就是 libnjb 的 **Perl 语言绑定（binding）**，让 Perl 程序也能调用 PDE 协议 API。
- 与本项目**完全无关**：我们用 Python + pyusb 自研协议栈，没有用到任何 Perl 代码，也不会引入这个已停更多年的组件。

## 2. libusb：我们用的是最新版 1.0.30

### 2.1 本地打包 DLL 的精确版本

直接读取 `src/runtime/libusb-1.0.dll` 的 `libusb_get_version()` 结构：

```
libusb DLL 版本: 1.0.30.12037
rc: ''  describe: https://libusb.info
```

所以文档里笼统写 "libusb-1.0" 虽然不算错，但**精确版本是 1.0.30**，而且恰好是当前上游最新稳定版（2026-05-17 发布）。这个 DLL 来自 `libusb-package` Python 包内置。

### 2.2 libusb 1.0.30 更新了什么（上游 ChangeLog）

- **Windows 热插拔支持**（`Add hotplug support on Microsoft Windows`）
- **WinUSB 后端新增 RAW_IO 支持**
- 修复 Windows 根集线器总线号重复分配问题
- 修复 MSVC 2026 编译问题
- 新增两个 API：`libusb_get_device_string()`（无需打开设备即可读设备字符串）、`libusb_get_session_data()`（返回系统相关 handle）
- 设备移除竞态、描述符解析内存安全、macOS 并发等多项稳定性修复

上一版 1.0.29（2025-06-01）主要是回归修复和 API 版本宏更新。

**对我们的意义**：RAW_IO 支持可能改善大批量 bulk 读取的性能（我们之前 57s 的瓶颈已通过缓存规避），但当前无需为此改动——现有传输路径已实测稳定。热插拔支持我们也没用到（播放是轮询模型）。

### 2.3 libusb-win32 是另一个项目，别混淆

你给的 `https://sourceforge.net/projects/libusb-win32/` 有效，但要注意它是**完全不同的项目**：

| | libusb 1.0（我们用的） | libusb-win32（你链接的） |
|---|---|---|
| API | `libusb_*`（1.0 API） | `usb_*`（0.1 API） |
| 内核驱动 | 依赖 WinUSB / WinUSB-INF | 自带 `libusb0.sys`（有数字签名） |
| 用户态 DLL | `libusb-1.0.dll` | `libusb0.dll` |
| 许可证 | LGPL-2.1-or-later | GPLv3 / LGPLv3 |
| 主仓库 | `https://github.com/libusb/libusb` | `https://github.com/mcuee/libusb-win32` |

- SourceForge 页写明：**2024-02-23 起开发迁到 GitHub**（`https://github.com/mcuee/libusb-win32`），SourceForge 现在只保留邮件列表。
- GitHub 上项目状态：**supported**（仍维护）。
- 最新版本 **V1.4.0.1（2025-08-22，snapshot）**，修复 BULK/INT 传输的 ZLP 问题；上一个正式版 V1.4.0.0（2024-02-22）修复了 BSOD、缺失函数等问题。
- 官方建议用 **Zadig 2.9** 来安装 libusb-win32 1.4.0.0 驱动。

**我们的项目不用它**：我们走的是 WinUSB 路线（自签 CAT + `winusb.sys`），上层用 pyusb/libusb 1.0.30。文档里提到 libusb-win32 只是作为 Zadig 可选目标驱动之一，这个描述是准确的，无需删除，但值得补一句"它属于 libusb-0.1 体系，与我们内置的不是同一个库"。
