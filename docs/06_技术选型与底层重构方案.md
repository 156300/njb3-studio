# NJB3 技术选型与底层重构方案（评审稿）

> 日期：2026-11-21  
> 状态：**评审稿，仅做方案记录；未选择、未实施、未修改源码**  
> 范围：NJB3 工具的底层协议、USB 控制传输、二进制协议栈、业务状态机与 UI 边界  
> 约束：现有 Python 程序是**已经真机验证过的参考实现**，任何重构都必须以它为黄金基准

---

## 0. 一句话结论

**底层协议、USB 控制传输和二进制协议栈用 Rust 重构，比继续堆 Python 更合理。**  
但不要做“整体重写”：先把底层抽成独立的 Rust 核心和服务，再通过稳定接口接 UI；UI 框架（React / Electron / Python 组件库）可以后面再选。

优先级应是：

1. **先解耦**：设备核心与 UI 分开，UI 只发命令、收事件。
2. **再固化**：把真机验证过的协议细节写成规范 + 黄金测试。
3. **后迁移**：逐模块迁到 Rust，每个阶段与 Python 输出对比。
4. **最后换 UI**：底层稳定后，再决定 React / Tauri / Electron / Python UI。

## 1. 现状盘点：为什么要重构

### 1.1 代码规模

| 文件 | 行数 | 方法数 | 当前职责 |
|---|---:|---:|---|
| `scripts/njb3_gui.py` | 5191 | 208 | UI 构建、事件循环、USB 任务编排、播放状态机、曲库/清单编辑、驱动安装、皮肤/布局 |
| `scripts/njb3_pde.py` | 1717 | 63 | PDE 协议栈、USB 传输、曲库/清单读取、上传下载、播放控制、设备恢复 |
| `scripts/njb3_transfer.py` | 511 | — | ID3 解析、M3U 解析、命令行传输封装 |
| `scripts/njb3_explorer.py` | 268 | — | 资源管理器树、系统图标、路径切换 |
| `ui_next/njb3_dock.py` | 650 | — | 可停靠面板引擎 |
| `ui_next/njb3_theme.py` | 337 | — | 主题系统、系统明暗跟随、对比度校验 |
| `ui_next/njb3_studio.py` | 451 | — | 新版 UI 壳，继承并覆盖原 `App._build_ui()` |

### 1.2 用户判断的核对

> “Python UI 只是负责调度。”

**部分正确。** 控件本身确实主要是调度入口，但 `njb3_gui.py` 里的 `App` 不只是 UI：它还承载了播放队列、曲库缓存、设备连接、任务串行化、30 秒校正、错误恢复等状态机。也就是说：

- UI 控件层：可以替换；
- `App` 里的业务状态：不能随 UI 一起丢；
- 真正的问题是**业务状态机被塞在 UI 类里**，导致没法独立测试、复用和迁移。

### 1.3 主要问题

1. **单文件过大**：`njb3_gui.py` 5191 行、208 个方法，任何改动都容易牵一发动全身。
2. **耦合严重**：UI 变量（`StringVar` / `DoubleVar`）、线程队列、USB 设备对象、业务逻辑混在同一个类。
3. **没有系统文档**：大量关键结论散落在代码注释、`使用说明.txt`、`USB接口指令清单.md`、`agent.md` 和历史对话里。
4. **二进制解析靠手工偏移**：`struct.unpack_from`、大端序、UCS-2、帧头长度都正确，但类型系统帮不上忙，改错一位很难发现。
5. **错误恢复经验不可编译**：12 字节 ping、写命令不能多发一次读、超时后 drain→release→reset→close 等只能靠注释守着。
6. **跨平台停留在 UI 层**：tkinter 皮可以换，WinUSB / PowerShell / libusb DLL 仍是 Windows 专属。

## 2. 目标架构

### 2.1 分层原则

```mermaid
flowchart LR
    UI[任意 UI 壳<br/>React / Electron / Python] --> IPC[稳定 IPC 契约<br/>command + event]
    IPC --> SVC[njb3-service<br/>单设备所有者 / 任务串行]
    SVC --> CORE[Rust 核心 crate 组]
    CORE --> SYS[libusb / WinUSB / 驱动适配]
    SYS --> DEV[NJB3 041E:4101]
```

关键规则：

- **UI 永远不直接碰 USB**。
- **同一时刻只有一个组件拥有设备句柄**。
- 所有长任务（上传、下载、读取曲库）通过事件回报进度，不阻塞 UI。
- 业务状态机在核心层，UI 只做展示和用户输入。

### 2.2 建议的 crate 划分

| crate | 职责 | 来自现有代码 |
|---|---|---|
| `pde-types` | VID/PID、frame ID、状态码、数据库 ID、错误类型、强类型 ID（TrackId/PlaylistId/FileId） | `njb3_pde.py` 常量段 |
| `pde-codec` | 大端整数、UCS-2、32 字节 CBSU 帧、元数据帧、ID3 帧解析/打包 | `u16be/u32be/str_to_ucs2/pack_songid3` |
| `pde-transport` | `rusb`/libusb 打开设备、capture/release、control/bulk 读写、send_only vs command、recover | `NJB3Device.open/close/recover/_ctrl/_bulk_*` |
| `njb3-device` | 设备会话、单飞任务队列、超时/重连策略、连接状态事件 | `NJB3Device` + GUI 的 `_worker` |
| `njb3-library` | 曲目/播放清单读取、元数据编辑、曲库快照、播放列表成员 | `list_tracks/list_playlists/get_playlist_tracks` |
| `njb3-transfer` | 上传、下载、删除、ID3 提取、M3U/文件夹导入 | `upload_track/download_track/njb3_transfer.py` |
| `njb3-playback` | 播放队列、观测驱动的自然前进、7 种播放模式、进度/位置双模型 | GUI 的 stage/playback 逻辑 |
| `njb3-service` | IPC/JSON-RPC、事件广播、配置持久化、日志、平台驱动适配 | GUI 的 queue/worker/log 部分 |

> 不必一开始建 8 个 crate。第一阶段可以先建 `pde-types`、`pde-codec`、`pde-transport` 三个核心 crate，其余按迁移进度拆出。

## 3. 底层实现语言对比

### 3.1 直接回答

| 选项 | 能不能做底层协议/USB | 结论 |
|---|---|---|
| **Rust** | 能，且很适合。`rusb` 直接封装 libusb，提供 `read_control` / `write_control` / `read_bulk` / `write_bulk` | **推荐做长期核心** |
| **Node / TypeScript** | 能，`node-usb` 通过原生模块封装 libusb，也有 WebUSB 风格 API | 可做过渡或 Electron 场景，但不是最稳的底层方案 |
| **React** | 不能。React 只是 UI 库，没有 USB/系统访问能力 | 只能放在 UI 层，不能承担协议栈 |
| **Python** | 能，且现在已经跑通。`pyusb` + `libusb-package` 可用 | **保留为黄金参考/迁移过渡，不建议继续加码** |

### 3.2 维度对比

| 维度 | Rust | Node / TS | Python | React |
|---|---|---|---|---|
| USB control/bulk | 高：libusb 原生绑定 | 中高：原生模块，需处理 ABI/打包 | 高：pyusb 已验证 | 无 |
| 二进制帧/大端解析 | 高：struct、enum、Result、类型安全 | 中：Buffer 手工偏移 | 中低：struct 手工偏移 | 无 |
| 并发与任务串行 | 高：Mutex/Actor 明确 | 中：事件循环 + 原生回调 | 中：线程 + GIL + 锁 | 无 |
| 错误 modeling | 高：`Result<T, E>` + enum | 中：异常/回调混杂 | 中：异常 | 无 |
| 打包部署 | 高：单二进制 + 少量 DLL | 中低：Node 原生模块 + 运行时 | 中：Python 运行时 + DLL | 依赖宿主 |
| 跨平台核心 | 高 | 中高 | 中高 | 不适用 |
| UI 生态 | 中（配 Tauri/Slint 可用） | 高 | 中高 | 最高 |
| 本项目的学习/迁移成本 | 中高 | 中 | 低（现成） | 中 |

### 3.3 为什么 Node 不是首选

`node-usb` 确实提供 `controlTransfer`、`bulkTransfer`、`reset` 等能力，也能在 Electron 中使用；但它依赖原生模块：

- Windows 上仍需 WinUSB/UsbDk，驱动绑定问题没有消失；
- Electron 的 WebUSB 有权限、blocklist、保护类设备限制；
- `usb-device-added/removed` 不是通用热插拔监听；
- 原生模块要处理 Node/ABI/预编译包与打包；
- 二进制协议的类型安全仍不如 Rust。

如果团队已经重度使用 TypeScript，Electron + `node-usb` 是可行的“第二方案”；但对这个项目的低位字节、状态字、超时恢复来说，Rust 更稳。

### 3.4 为什么 Python 仍保留

Python 版本不是“技术债”，而是**资产**：

- 它包含所有真机验证过的协议细节；
- 它有历史回归测试和实机结论；
- 它可以作为 Rust 迁移的对比基准。

建议把它改名为“参考实现 / golden implementation”，在迁移完成前**只读保留**，不再新增大功能。

## 4. IPC 接口契约草案

### 4.1 命令

```json
{"id": 1, "method": "device.connect", "params": {}}
{"id": 2, "method": "library.listTracks", "params": {"extended": true}}
{"id": 3, "method": "transfer.upload", "params": {"paths": ["D:/01.mp3"]}}
{"id": 4, "method": "playback.playQueue", "params": {"trackIds": [12, 34, 56], "start": 0}}
{"id": 5, "method": "playback.seek", "params": {"ms": 65000}}
```

### 4.2 响应

```json
{"id": 2, "ok": true, "result": {"tracks": []}}
{"id": 3, "ok": false, "error": {"code": "NeedWinUSB", "message": "设备仍被 Creative 驱动占用"}}
```

### 4.3 事件

```json
{"event": "device.connected", "data": {"firmware": "1.40.06", "capacity": 60000}}
{"event": "task.progress", "data": {"taskId": 3, "current": 7, "total": 20, "text": "01.mp3"}}
{"event": "playback.position", "data": {"elapsedSec": 73, "queuePos": 2, "state": "playing"}}
{"event": "log", "data": {"level": "error", "text": "USB timeout"}}
```

### 4.4 契约原则

1. 命令有 `id`，响应必须带回 `id`。
2. 长任务用事件，不靠轮询 UI 状态。
3. 错误用稳定 `code`，UI 根据 code 做提示，不解析中文文案。
4. `playback.position` 与进度条状态分开，保留 v26 的双模型。
5. 配置 schema 带版本号，避免旧布局/皮肤文件破坏新程序。

## 5. 分阶段迁移路线

| 阶段 | 目标 | 交付物 | 验收标准 |
|---|---|---|---|
| P0 文档冻结 | 把散落结论收拢成规范 | 本方案 + PDE 接口契约 + 真机不变量清单 | 关键结论有出处，评审通过 |
| P1 纯逻辑原型 | 不接设备，先迁编解码 | `pde-types` + `pde-codec` + 黄金向量测试 | 与 Python 对同一字节流输出一致 |
| P2 传输层 | 打通真实设备 | `pde-transport` + `njb3-device` | capture/ping/disk/battery 与 Python 一致；超时可恢复 |
| P3 业务模块 | 迁曲库/清单/传输/播放 | `njb3-library`、`njb3-transfer`、`njb3-playback` | 真机读取结果与 Python 快照一致 |
| P4 服务化 | UI 与核心解耦 | `njb3-service` + IPC 契约 | 用 mock UI 能完成全流程 |
| P5 UI 选型 | 再决定前端壳 | Tauri/Electron/Python UI 原型 | 拖拽、停靠、主题、树、虚拟列表可用 |
| P6 并行切换 | 双轨运行再替换 | 安装包 + 回归清单 + 回滚方案 | 真机全功能通过，回滚可恢复 |

**决策门**：

- P2 结束后决定“核心是否继续用 Rust”；
- P5 结束后决定“UI 用哪套”；
- P6 之前不删除 Python 版本。

## 6. 必须固化的真机不变量

这些不是普通注释，是要写进测试和规范的硬约束：

1. 设备 `041E:4101`，USB 1.1，Bulk OUT `0x02`，Bulk IN `0x82`。
2. 控制传输：`bmRequestType=0x21`，`bRequest=0xFD` capture / `0xFE` release。
3. PDE 帧头 32 字节：`CBSU` + 4 零字节 + 4 字节大端长度 + 20 零字节。
4. ping **只发前 12 字节**；发 14 字节会导致后续命令错位。
5. 读操作用 `command()`（发帧后读返回）；写操作用 `send_only()`（只发帧，状态另读）。
6. 电池 `0x0114` 返回百分比，不是电压；85 就是 85%。
7. `0x0105` 是曲库元数据里的曲目总时长；固件没有“读当前曲目总时长”命令。
8. `0x010C` 是只写 seek 毫秒；`0x010F` 是播放列表名。
9. `0x000C` 在曲目库是 TrackID，在播放清单库是 PlaylistID。
10. 固件返回的是队列位置和已播秒数，**不返回当前曲目 ID/曲名/总时长**。
11. `play_track` 插队首，`queue_track` 追加队尾；设备会自然向前播放，不要逐曲主动切歌。
12. 播放位置标题始终每秒走动并每 30 秒校正；进度条在识别不到曲目时冻结。
13. 超时恢复顺序：读空残留 → release → reset → dispose/close；不要直接长阻塞 ping。

## 7. 风险与缓解

| 风险 | 表现 | 缓解 |
|---|---|---|
| 固件怪癖 | Rust 按文档实现但真机不通 | 所有命令对比 Python 字节流；P2 真机门禁 |
| 驱动互斥 | Creative 驱动占用导致 Access denied | 单设备所有者；明确切换 WinUSB；封装 recover |
| WebUSB 限制 | 权限/blocklist/缺 reset | 不作为主路径，仅做实验 |
| Node 原生模块打包 | ABI、预编译、运行时体积 | 若选 Electron，优先把 USB 放独立 Rust 服务 |
| UI 重写范围失控 | 只顾换皮，底层没解耦 | 先完成 P0-P4，再启动 P5 |
| 用户配置迁移 | 布局/皮肤/队列缓存丢失 | 配置 schema 版本化 + 导入旧文件 |
| 跨平台误解 | UI 跨平台但设备层仍 Windows-only | 抽象 `UsbBackend` trait；Windows 先做透 |
| 状态机回归 | 队列顺序/切曲/进度错乱 | 复用真机不变量清单做 golden tests |

## 10. 本轮结论

- **底层用 Rust 重构是正确方向**，但不是因为“Rust 流行”，而是因为它能把字节解析、错误分支、USB 状态机和任务串行化变成可编译、可测试、可维护的结构。
- **Python UI 层可以换，Python 参考实现不能丢**：它是迁移期唯一可靠的真机基准。
- **React 不参与底层**；Node 可做备选壳；Python 只做过渡/参考；Rust 做核心。
- 本文件只是评审稿：**下一步应先细化 P0 的《PDE 接口契约》和黄金测试清单，而不是直接动源码。**
