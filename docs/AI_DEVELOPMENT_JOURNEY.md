# AI 辅助开发学习过程全记录

> 本文把 NJB3 Studio 从「一台 Win11 上认不出来的老 MP3」到「可发布的绿色软件」的全过程汇总成一篇文档。
> 重点是**判断依据、踩过的坑和真机数据**，供后来者复用方法，而不是复述代码。

---

## 0. 起点：先判决可行性，再动手

面对一台 2003 年左右的 Creative Nomad Jukebox 3，第一件事不是写代码，而是回答三个问题：

| 问题 | 结论 | 依据 |
|---|---|---|
| 能否在 Win11 上稳定驱动并传歌？ | ✅ 可以 | 原厂驱动本身能在 Win11 工作，失败在安装包解压与检测方式 |
| 能否当 U 盘直读 / 拷进去就识别？ | ❌ 不行 | 设备是私有 PDE 数据库协议，不是大容量存储；固件加密打包、无 SDK |
| 能否把 USB 1.1 升级到 USB 3.0？ | ❌ 物理上不行 | 速率由 SoC 内 USB PHY 决定，固件改不了硬件 |

这一步的价值：**把不可能的方向早早关掉**，避免在固件逆向和硬件改造上耗尽时间。可行路线只剩一条——
用 WinUSB 替换原厂内核驱动，在用户态实现 PDE 协议。

---

## 1. 驱动攻坚：最漫长的一段弯路

### 1.1 问题现象

原厂 CMS5 在 Win11 上检测不到产品并秒退。设备管理器显示 Creative 驱动（ctpdusb.sys），
它独占 USB 端点，导致 libusb 打不开设备。目标：换成微软自带的 winusb.sys，用自定义 INF + 签名 CAT 绑定。

### 1.2 关键坑：CAT 签名 digest

替换驱动需要合法签名的 catalog 文件。最初生成的 CAT 总是报：

```
0x80096010 TRUST_E_BAD_DIGEST → 安装退出码 7 / 0xE0000247
```

排查走了几轮：

1. 先怀疑证书链，做了证书放入 `LocalMachine\Root` 与 `TrustedPublisher`、私钥权限检查；
2. 再怀疑 INF 的 member 列表（HWID1 / OS / File / OSAttr 是否齐全）；
3. 最后对比 **libwdi（Zadig 同款）的权威源码**才发现：CAT 里的文件哈希必须是
   **二进制 `04 14 + 20 字节 SHA1`**，而我最初写成了 UTF-16 的 hex 字符串。

用 Python `ctypes` 精确封送 `CryptCAT*` / `SignerSignEx` 系列 API，复刻 libwdi 算法后，
自测得到 `WinVerifyTrust=0x800B0109`（只是证书信任尚待系统确认），不再是 digest 错误。
驱动切换终于跑通，设备枚举 OK、`libusb_open` OK，iProduct 返回 `NOMAD Jukebox 3`。

**收获**：Windows 驱动签名错误信息非常笼统，必须找到权威实现做二进制级对照，不能靠猜。

### 1.3 连接管理重构

驱动通了之后又出现「能读固件但所有功能超时」。逐帧排查发现 **ping 命令长度写成了 14 字节，实际应为 12**，
多出的 2 字节让设备一直等待后续数据。修掉后协议命令全面恢复。

随后重构连接模型：持久连接 + 显式断开按钮 + 掉线弹窗 + 线程安全 + 关窗释放。
早期每次操作都重新 open/close，既慢又容易让设备进入异常状态。

## 2. 协议栈：用 libnjb 当地图，但不照抄

NJB3 使用 PDE series-3 私有数据库协议：CBSU 32 字节头 + body，OUT 端点 0x02 / IN 端点 0x82，
控制传输用 0xFD/0xFE 做 capture/release，字符串是 UCS-2BE。

### 2.1 曲库分 28 批读取

第一版 GUI 只显示 208 首，用户指出真机实际是 4829 首。逐批抓包后确认：

- 曲库按游标分批返回，共 28 批；
- 结束标志是**批尾零长度帧之后的 `read_again`（word5，末批为 1）**；
- `word4` 恒为 `0x00010000`，**不能**当结束标志——这正是上一版只读到 208 首的原因。

按 libnjb 的游标机制跨批累加后，真机读到 4829 首，ID 全唯一，artist/filename/folder 4829/4829、
title 4827，9 个播放列表中文名正确。

### 2.2 播放列表只显示 1 个的 bug

播放列表项之间用 **2 字节帧**分隔，libnjb 对任意 2 字节帧都会结算。旧代码只认 `frameid=0`，
导致 9 个列表被覆盖成 1 个。修正分隔帧处理后恢复正常。

### 2.3 播放队列的攻坚

当前播放队列没有公开文档。通过只读探测 + 解析原始返回数据，逐步确认队列顺序规则：
**写入追加到队尾、播放从队首取**，并实现了队列读取与拖拽排序写入。
这条路线后来成为「播控工作台」的基础。

## 3. 界面：从三页签走到三工作台

界面经历了几轮方向调整，值得记录的是**做错后回退的决策**：

1. 最早是三页签 + 常驻传输列表；
2. 试过完整 `.ui` 文件 + Qt 设计器工作流、foobar2000 风格皮肤、PyQt-Fluent 独立应用；
3. 结论：这些路线要么引入重依赖、要么与已有业务逻辑割裂，**全部回退**；
4. 最终方案：Python `tkinter` + 自研 `njb3_dock.py` 可停靠框架，
   用**子类化**复用 `njb3_gui.py` 的全部业务逻辑——新版界面一行业务代码都不重写。

三工作台定为「传输 / 播控 / 控制」，整页切换无页签栏；控制工作台内部模块可拖动、贴边、调大小；
分隔条 4px、折叠栏 14px；主题支持深浅双套并跟随系统。

这一阶段最大的教训来自「复制框体」：复制粘贴窗体代码后，右键菜单命令延迟执行时
引用的是**事后恢复的临时树**，导致按钮串页、删错歌。修复方式是**菜单生成时绑定事件来源树**，
并为此加了整套回调归属审计。

## 4. 播放控制：一次失败的重做

用户反馈「播放到最后会滞后约 1 秒」，第一版优化用了 **300ms 高频轮询 + 0.35s 提前量 + 双重触发**。
真机结果更糟：曲目乱跳。

处理方式是**先停下改代码，做只读联调**：

- 找最短曲目（约 43 秒）做样本；
- 每秒采样播放位置，实测 `play_track` 命令延迟 0.5~1.1s，只读命令 3~6ms；
- 确认设备播放全程 `state=0(playing)`，播完**不会**报 stopped；
- 中途 `play_track` 会立即切歌；设备时钟与 PC 近 1:1。

基于这些事实，v44 撤销高频与提前量，回到**单一本地计时 / ended 触发**，连播 3 首验证无乱跳，
尾部误差 ≤1s，每次只切一次。

同时定下一条纪律：**任何真机脚本退出前必须 STOP → clear queue → recover → close，并复核状态**。
曾经因为诊断脚本被管道 `| head` 强杀、没执行归还流程，导致设备卡死。此后严禁管道截断诊断输出。

## 5. 性能：57 秒到底卡在哪

用户对比官方 CMS（WinXP 模拟器下几秒导入歌曲列表）质疑我们慢。逐阶段真机计时：

| 阶段 | 耗时 |
|---|---:|
| 打开设备 | 0.12s |
| 设备信息（固件/容量/电量/音量/EAX） | 0.17s |
| **曲库 `list_tracks(extended=True)`** | **56.83s** |
| 播放清单 + 9 个清单成员 | ~4.0s |
| 当前队列回读（固件不支持，回退缓存） | 0.04s |

总计约 62 秒，**91% 卡在曲库扩展读取**。

排除过程：

- bulk read 从 1MB → 64KB → 4KB，耗时仍约 57s ⇒ 不是 WinUSB 驱动或主机读包长度问题；
- `list_tracks(extended=False)` 同样 4827 首仅 3.27s，快约 17 倍；
- 基础字段之上单独加 `F_FNAME(0x0007)` 或 `F_FOLDER(0x000D)` 任一，都会回到约 56s。

结论：**慢在固件逐首查询文件名/文件夹，约 11ms/首**。官方 CMS 快，很可能就是只读基础字段。

### 5.1 解决方案：按设备序号缓存

- 主键：`read_id()` 的 16 字节 hex，真机验证稳定，首次读取 0.87s、之后 3ms；
- 缓存只存慢字段 `filename` / `folder`，按 trackid 索引；
- 每次连接仍从设备读最新基础曲库（3.3s），缓存只补扩展字段 ⇒ 设备增删歌曲不会被旧缓存覆盖；
- 序号不匹配 / 缓存损坏 / 版本不符 → 自动退回完整读；
- 提供「刷新完整曲库和播放清单(速度慢)」按钮手动更新缓存。

真机验证：首次完整读 57.12s / 4827 首建缓存；再读 3.20s / 4827 首、扩展字段 100% 补回；
强制刷新 57.13s 后缓存更新。

## 6. 方法论总结

1. **先判决可行性**：用硬件事实和物理约束砍掉不可能的方向。
2. **证据优先于猜测**：驱动签名靠权威源码二进制对照；协议靠逐帧抓包；性能靠逐阶段计时；播放行为靠真机采样。
3. **不确定时先审计、不改代码**：设备卡死时先复现与定位，确认不是软件问题再动。
4. **复用而不是重写**：新版界面子类化旧业务，避免几千行逻辑重写引入回归。
5. **回滚也是一种进步**：PyQt、设计器、高频轮询等路线被证伪后及时撤销，比硬撑更省时间。
6. **设备归还纪律**：真机脚本一律 `try/finally` 完整归还，禁止管道截断输出。
7. **回归测试兜底**：每个版本都补测试；最终 19 套、约 500 项断言全过才打包。

- 源码、测试、诊断脚本、协议文档与本文一并公开。
