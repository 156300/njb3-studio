# NJB3 USB（PDE series-3）可用接口与功能清单

整理时间：2026-11-20（v15）
适用设备：Creative Nomad Jukebox 3，VID `041E` / PID `4101`，固件 1.40.6，WinUSB + pyusb/libusb。

## 证据来源与可信度

- **权威协议来源**：libnjb 2.2.7 `src/protocol3.c` / `protocol3.h`，其中明确列出了 PDE 命令号、帧 ID 和状态字。本项目的字节序列基本按该实现移植。
- **真机证据**：此前同一连接内验证过固件、容量、4829/4831 首曲库、9 个播放列表及成员、新建/改名/删除列表、上传、元数据写回、播放/暂停/停止/恢复、seek。
- **官方软件逆向**：对原目录只读解包 `NMEX_PCApp_3_01_10.exe`，确认是 InstallShield 外层 CAB，内部 `data1.cab` 为私有 `ISc(` 容器；成功解出中文资源 `JBNSRes.dll`，看到“无法重命名选定的播放列表 / 无法将所选项目添加到播放列表”等文案，但没有可直接提取的明文 PDE 命令数组。CMS5 等安装包同样是打包器封装。官方 PC 端的可操作命令因此以 libnjb 实现为准，没有凭空编造。
- **实验项**：读取“机器当前队列”的 `0x0008 + 帧 0x011C` 是依据协议头把 `0x011C` 标注为 PLTRACKS，以及入队命令写同一帧推导出来的；本轮设备离线，**尚未真机验证**。若设备返回 NOTIMPLEMENTED 或空数据，软件会提示并回退到“载入机器播放列表”。

## 状态字

`0x0000` OK；`0x0001` EMPTY；`0x0002` 传输出错；`0x0003` 文件大小非法；`0x0004` 未实现；`0x0005` 不存在；`0x000C` 受保护；`0x000E` EMPTY_CHUNK（分批结束、空列表、清队列成功常见）。

## v15 新增命令字节

- 清空队列：`01 03 00 01 00 00 FF FF`
- 入队：`01 04 00 01 FF FF 00 06 01 1C <trackid:4大端> 00 00`（共 16 字节）
- 播放曲目：`01 00 00 01 <trackid:4大端> 00 04 01 19 00 00 00 00`
- 读取当前队列（实验）：`00 08 00 01 FF FE 00 02 01 1C 00 00`，再按通用帧解析。
- 重排机器播放列表：series-3 没有原地排序命令。实现为“新建同名清单 → 按新顺序整批加曲目 → 删除旧清单”，因此**播放列表 ID 会变化**，软件会更新缓存。

## v17 新增：音量 / EAX / 播放模式 / 播放队列多策略读取

**术语统一**：原“播放列表”（数据库里约 10 条、含成员）统一叫【播放清单】；
机器已加载可直接放音的易失队列（原“设备队列/选定音乐”）统一叫【播放队列】。

- **音量读取**（`get_volume`）：EAX 请求命令 24 字节——
  `02 00 00 01 02 05 00 00 00 1e 3c 00 00 08 02 01 02 02 01 0e 02 <帧ID:2> 00 00`，
  帧 ID 在偏移 4 和 20 都写 `0x0203`。回包按帧解析：`0x0201`=MINMAX(min,max)，
  `0x0203`=当前值。libnjb `njb3_read_eaxtypes` 权威模板。
- **音量/EAX 参数写入**（`adjust_eax`，libnjb `njb3_adjust_eax`）：
  带值 22 字节 `02 01 00 01 <eaxid:2> <patch:2> 00 04 02 02 00 01 00 04 <eaxid:2> <value:2> 00 00`；
  不带的预设选择为前 16 字节。eaxid：`0x0203` 音量 / `0x0204` 环境 / `0x0205` EQ /
  `0x0206` 空间化 / `0x0207` 时间缩放 / `0x0208` 智能音量。
- **EAX 总开关**（`set_eax_master`）：写寄存器 `0x020A`——
  `00 07 00 01 00 04 02 0a <0/1:2> 00 00`。
- **播放模式（v18 结论：PDE 无此命令）**：libnjb 全源码只有播放控制
  （`0x010b` PLAYINFO：播放/停止/暂停/恢复）与 `0x0119` 指定曲，**没有任何
  repeat/shuffle/mode 设置命令**。`0x0116/0117/0118` 是静态寄存器（写它机器
  不切换模式）。因此 v18 起 7 种播放模式**全部由本程序控制**：用 `play_track`
  单曲播放 + 本地队列顺序/游标，播完自动按模式切下一曲。原 `set_play_mode`
  探测接口保留但不再依赖。
- **播放队列回读（v18 真机诊断结论 —— 固件不开放，无解）**：真机诊断回包：
  ```
  [011C] status=0x0000 raw=00000000            → 寄存器命令读数据库帧，返回空
  [0119] raw=...0119 012d...                    → 当前队列位置(或当前曲目)，标量
  [0116]=00000183 [0117]=00000187 [0118]=00509ec4 [011A]=1a04 → 标量寄存器
  [0120]=0001fffe0011                           → 与 libnjb 注释官方样本一字不差
  ```
  libnjb 全源码只有 `njb3_queue_track`(0x0104 入队) / `njb3_clear_play_queue`(0x0103)
  / `njb3_current_track`(0x0119 位置)，**没有整条队列回读**。v18 新增用数据库实体
  命令 `0x0108 + entity_id + 0x000C(POSTID)` 再尝试一次；失败仍回退本地
  `play_queue_cache.json`（写回队列时同步保存）。诊断窗口已写明结论。
- **当前队列位置**：`get_current_track()` 返回的是**播放队列位置**而非曲目 ID
  （libnjb `njb3_current_track` 明确注明 “position in the current play queue”），
  界面显示格式固定为“当前号/总数”，如 `[3/12]`。

## v18 新增：真机问题修复（音量/EAX/标尺）

- **音量 MINMAX 解析修正**：`0x0201` 帧载荷格式为 `占位(2) + max(2) + min(2)`
  （libnjb `parse_eax_block`: dp[6]=max, dp[8]=min）。旧代码读 `payload[4]/[6]`
  把上限读成下一帧长度(=2)，导致“音量只能到 2”。正确：max=`payload[2:4]`、
  min=`payload[4:6]`。机器音量刻度 0-25。
- **EAX 总开关读取修正**：`get_eax_master` 旧代码读 `raw[2:4]`（帧长度，常为 4，
  永非零）导致机器没开放 EAX 也打钩。正确：状态字后按帧解析 `0x020A`，值为 1
  才开启；读不到抛错，UI 不打钩且禁用调参。
- **EAX 写入不丢连接**：`adjust_eax`/`set_eax_master` 的读状态改用 `_status_tolerant`
  （超时返回 None 不抛），避免未开放 EAX 时读状态超时触发 recover 断连。

## v16 新增：设备队列写回

- “当前播放清单”在本版统一指**设备队列**（易失的选定音乐队列），不是播放列表。
- 连接后自动调用 `read_current_queue()` 回读设备队列；播放控制页“↻ 读取设备队列”可手动重读。
- 写回整条队列 `replace_play_queue(ids)`：`01 03 00 01 00 00 FF FF`（清空）后，
  对每个曲目依次发 `01 04 00 01 FF FF 00 06 01 1C <trackid:4大端> 00 00`。
  该操作只改队列、不启动播放；界面按钮为“写回设备队列”。
- 左右两侧（列表内歌曲 / 机器内歌曲）均可拖入中间设备队列，队列内拖动即排序，
  写回时按界面顺序逐首入队。

## 可以继续增加的功能

1. ~~**音量/EAX 调参面板**~~：v19 已取消（不好用且无实际意义），仅保留 EAX 勾选开关与 0-25 音量条；协议层函数仍保留供音量设置用。
2. **设备时钟**：`0x0110` 可读写，显示/同步设备时间。
3. **设备密钥**：`0x000C` 读取 AR00/PL00 等，可能揭示官方软件校验流程；只读安全。
4. **文件/文件夹管理**：`0x0006`/`0x000A`/`0x0005` 已具备基础，可增加数据文件下载、批量整理。
5. **关机位图**：`0x000B` 相关位图写入已有 libnjb 参考，但需要 132×64 单色位图转换。
6. **更强舞台模式**： cue 点（用 seek 存每个曲目的入点）、淡入淡出（若无固件 DSP 支持只能在 PC 侧 mixes 后上传）、演出清单导入导出 JSON/CSV。
7. **1394/FireWire**：独立私有 FWFDO 通道，libnjb 未实现；理论可逆向抓包但不是 USB 命令扩展，不能复用现有代码。

## 明确做不到 / 不应承诺

- 固件刷成 USB 声卡：设备没有 UAC 接口，USB 描述符也没有等时端点；换驱动不能改变设备枚举。
- 异步播放通知：libnjb 只提供轮询 `get_elapsed_time()` / `current_track()`，没有事件通知。
- 原地重排播放列表：协议没有该命令，只能重建清单。
- 完全可靠的机器当前队列回读：`0x011C` 读取是实验路径；不支持时必须回退到机器播放列表。

## v19 复核：机器“選定的音樂”（Playing List）能否回读

**用户线索**：播放队列在机器上显示的名字是繁体“選定的 music/選定的音樂”。据此重新核对。

**核对方法**：完整枚举 libnjb 2.2.7 `src/protocol3.c` 全部 `njb3_*` 命令函数。

**结论（确定，非推测）**：与队列相关的命令只有四类——
- `njb3_current_track()`（0x0008 + 帧 0x0119）：返回【队列位置】标量，不是曲目 ID；
- `njb3_queue_track()`（0x0104）：写，入队；
- `njb3_clear_play_queue()`（0x0103）：写，清队列；
- `njb3_play_track()`（0x0100）：写，播放（会隐式清队列）。

**没有任何“回读整条队列/Playing List 清单”的命令**；`NJB3_PLTRACKS_FRAME_ID 0x011C`
是 `add_multiple_tracks_to_playlist()` 的【写入】帧，0x0116-0x0120 是静态寄存器。
故“選定的音樂”清单不能被软件读回，软件以本地缓存（`play_queue_cache.json`）+ 播放清单写回为准。
面板标题与【诊断】窗口已改用机器原名说明，避免误解为软件缺陷。

**v19 交互修复（不涉及新协议命令）**：
- 取消 EAX 调参（保留勾选开关）；音量条固定 0-25 刻度并加刻度数字；
- seek 后主动 0.35/1.1/2.2 秒三次强制同步 + 2.5 秒陈旧值保护窗，解决“进度从 0 慢慢同步”；
- 进度标尺首尾时间标签贴边对齐，完整显示；
- 全局点击回调加 `focus_set()`，让选中/失焦配色（含播放队列淡黄）真正生效。

## v20：音量数值语义探测 + 播控模式（软件实现）

**音量语义**：EAX 音量寄存器 `0x0203` 数值域未文档化，可能是档位(0-25)或百分比(0-100)。
`probe_volume_scale(38)`：写入非 4 倍数的 38 再回读——
- 回读≈38 → 百分比域（音量条 0-100，直发）；
- 回读为 36/40 等 → 百分比量化到 4% 步进（音量条 0-25，发送 档位×4）；
- 回读落在 0-25 → 档位域（直发档位）。
探测后恢复原音量。GUI 顶部【校准】按钮可手动重跑。**不新增 PDE 命令**，仅复用
`get_volume`(0x0203 帧) 与 `set_volume`(adjust_eax 0x0203)。

**播控模式**：因 libnjb 权威源码确认 series-3 固件**无“按队列位置播放”命令**，
只有 `play_track(trackid)`（会把曲目放到队首），且无整条队列回读——
- 机器序号是【软件本地维护的逻辑映射】(trackid→序号)，非固件真实寄存器；
- 播放以 trackid 定位清单条目，保证同一首歌不重复入队、不重复播放；
- 写回默认增量（只写未写入曲目，用 `queue_track` 0x0104），重刷用
  `clear_play_queue`(0x0103) + 逐首 `queue_track` 并按清单重新编号 1..N；
- 序号本地持久化（play_queue_cache.json 增 mseq 字段），跨会话保留。
**限制**：固件不开放队列回读，软件无法校验机器内序号是否与本地一致，
以本地记录为准；如需强制对齐，用【重刷队列】全量重写。

**其它 v20 修正**：焦点高亮改为显式 tag（失焦取消高亮、焦点在哪哪高亮，
ttk.Treeview 无 tag_add，须用 item(iid,tags=...)）；断开/停止后进度归零；
播放控制 6→8 按钮（加上一曲/下一曲，按框宽自动 1×8 或 2×4）。

## v21：真机队列顺序规则（新证据）+ 音量回退 0-100

**信息来源**：用户真机操作观察（2026-11-20），不是 libnjb 静态推断。观察结果：
> 先播放其他栏 A → 写入 B、C → 播放 D → 导入 E 并写入 → 播放其他栏 F，
> 机器队列最终顺序为 **F D A B C E**。

**推导出的规则**：
| 操作 | PDE 命令 | 机器行为 | 本地表现 |
|---|---|---|---|
| 写入播放队列 | `queue_track`（0x0104） | **追加队尾**（FIFO：先写排上、后写排下） | 新曲目移到清单末尾 |
| 播放选中曲目 | `play_track`（0x0100） | **插到队首**（LIFO/unshift：后播在前） | 该曲目移到清单首位 |

逐步验证：A → [A]；写 B/C → [A,B,C]；播 D → [D,A,B,C]；写 E → [D,A,B,C,E]；
播 F → [F,D,A,B,C,E]，与观察完全一致。

**软件适配**（`njb3_gui.py`）：
- `stage_tracks` 顺序严格等于机器队列顺序；`_mseq` 改为“当前队列位置 1..N”，
  不再是写入时分配的固定序号。`_renumber_mseq()` 在每次播放/写入后重算。
- `action_play_selected()`：已在清单的曲目移到首位（不新增重复条目）；
  不在清单的曲目插到首位；随后调用 `play_track(trackid)`。
- `action_stage_go()`：播放前把目标曲目移到 0 位再播（与 unshift 对齐）；
  手动播放重置自动播放计数器。
- `action_stage_save_queue()`：只写未写入曲目，按清单相对顺序逐首 `queue_track`；
  写入完成后由主线程事件 `stage_queue_written` 把这些曲目移到清单末尾并重算序号。
- 上一曲/下一曲：播放后队首是当前曲目，下一曲取队列第二首；上一曲按 `_play_history` 回退。
- 自动播放：`normal`/`shuffle` 用 `_auto_advance_pos` 计数，播完一轮即停止；
  `repeat_all`/`shuffle_repeat` 循环。

**音量**：`probe_volume_scale(38)` 方案在真机上表现为“能调小不能调大”，已停用。

## v23：播放总时长同步（0x0105 曲库元数据帧的正确用法）

**用户疑问**：进度条总时长不对，是不是没用 `0x0105 时长 → 进度条总时长` 帧？

**核查结论（证据：libnjb 2.2.7 源码 + 本侧协议栈）**：
- `0x0105 / F_LENGTH` 确实代表曲目时长，但它是**曲库元数据帧**：只出现在
  `protocol3.c:2280` 的 `njb3_get_track_tags[]` 元数据 wishlist 中，由
  `list_tracks()` 全量扫描曲目数据库时解析（本侧 `njb3_pde.py:668`），
  缓存进 `track['length']`。
- **PDE 播放接口（play / elapsed / current_track / seek / ctrl）没有任何
  “读当前播放曲目总时长”命令**；libnjb 全部 7 个 play API 也不存在此能力。
  因此“播放时读 0x0105”在协议上不可能，总时长只能来自本地曲库缓存。
- 原软件的缺陷：`0x0105` 解析出的 `length` **只在 `action_stage_go()`（播放选中/
  GO/切歌）被写入总时长**；“▶播放/恢复”走 `action_play_ctrl()` 纯控制命令、
  “查询状态”走 `play_sync` 观测（只更新状态/位置/已播秒数），两条路径都不碰
  总时长 → 停留在默认 05:00，且查询状态也无法补齐。

**修复（`njb3_gui.py`）**：
- 新增 `_sync_duration_from_track(track=None, reason="")`：按①显式曲目 →
  ②设备回报 `queue_pos` 映射 `stage_tracks[pos]` → ③`play_track_info` →
  ④`play_track_id` 查 `tracks` 的优先级，取 `length` 写入总时长（触发刻度重算）。
  用 `_duration_synced_tid` 记忆来源曲目：**同一曲目不覆盖用户手改值，换曲才重取**。
- 接入四条路径：`action_stage_go`（统一替换原直接 set）、`play_state_set`（▶播放/
  恢复）、`action_play_status`（查询状态）、`play_sync`（设备位置同步，含 v22 自然
  前进换曲，同时同步 `play_track_info`/`play_track_id` 保持一致性）。
- probe 新增 `duration_from_cache`，打包 exe 为 True。

**测试**：新增 `test_v23_duration_sync.py` 19 项全过；全量 21 套回归通过。

## v24：接口能力边界（当前曲目为何“查不到”）+ 播放信息归位

**用户问题**：手动清空机器播放队列、加入两首歌，连软件点播放后“当前曲目不对、
进度条不对、查询状态也查不到”——是程序错、接口调用错，还是根本没有接口？

**源码铁证（libnjb 2.2.7）**：
```c
/* This function only returns the position in the current play queue. */
int njb3_current_track(njb_t *njb, u_int16_t *position) { ... }
```
- `current_track` 只返回**队列位置**（第几首，0-based），**不返回 trackid / 曲名 / 总时长**。
- `elapsed_time` 只返回**已播秒数** + change 位。
- `libnjb.h` 的 playapi 段仅 7 个函数（Play/Queue/Stop/Pause/Resume/Seek/Elapsed），
  **没有任何**“读当前曲目元数据 / 读当前 trackid / 读总时长”命令。
- 结论：**接口能力缺失**，不是程序 bug 也不是调用错误。此前“当前曲目/总时长”
  都是软件拿队列位置去本地曲库/清单缓存**匹配推算**出来的（v23 的 0x0105 时长
  同样来自曲库缓存，0x0105 本身是曲库元数据帧而非播放态可读帧）。
- 后果：机器内队列被手动改动、而软件本地清单未同步时，按位置匹配的曲目/时长会错；
  固件无队列回读命令（v19 结论），只能由用户点【读回队列】导入后再播放。

**软件改动**：
- 播放控制框体：删“上一曲/下一曲”（固件无此命令）→ 6 按钮（2 行×3）；
  标题动态显示“当前播放位置 XX:XX”（来自设备 elapsed，真实回读值）。
- 当前曲目/进度条/总时长/刻度/状态整体上移进【播控模式】框体（本地清单所在处）。
- 焦点配色重写：`style.map(Treeview, background=[], foreground=[])` 移除主题
  selected 深蓝底（它覆盖行 tag，是 v20 起配色失效的根因；须在 `_build_ui` 后
  再配置一次，因主题在首控件创建时才加载）；焦点树选中行=灰蓝 `hot`、失焦
  普通树=灰 `cold`、失焦 stage_tree=淡黄 `warm`。

## v25：实机取数甄别（电池 / 时间 / 各类 ID / 时长 / 定位 / 播放列表名）

**取数脚本**：`build/probe_v25_interfaces.py`（实机连接，逐项打印原始字节与进制换算）。
**取数时间**：2026-11-21，固件 1.40.6，同一连接内全项只读（`0x010C` 是写命令，未发）。

### ① 电池 `0x0008 + 帧 0x0114` —— 返回的是【百分比】，不是电压

实机原始回包：`00 00 00 06 01 14 14 02 00 55 00 00`
```
00 00        状态 0x0000 OK
00 06        帧长 6
01 14        帧 ID 0x0114 电池
14           固定前导 0x14（libnjb 注释：always 0x14）
02           供电码：0=外接电源充电中 / 1=外接电源已充满 / 2=电池(未接电源)
00 55        16bit 电量 = 0x0055 = 85（2进制 00000000 01010101）
```
- **结论**：固件回的 16bit 值**就是百分比 0-100**，不是电压。libnjb
  `sample/handshake.c:139` 直接 `printf("Battery level: %d%%", battery_level)`。
- 旧版按 `level/0x400*100` 折算 → 把 85% 显示成 **8%**，这就是“电量显示不准”的根因。
  v25 已改为直接用原始值（85 → 85%），并钳制 0-100。
- 本次实时状态：85%、电池供电（未接电源）、未充电。

### ② `0x0007` / `0x0008` 里的“时间”是【设备墙上时钟 RTC】，不是播放时间

`0x0110` TIME 帧实机：`00 00 00 0a 01 10 06 04 04 20 20 12 02 19 00 00`
```
帧载荷（去状态/帧长/帧ID）：06 04 04 20 20 12 02 19   —— 8 字节 BCD
  libnjb 定义：星期(06=周六) 日(04) 月(04) 世纪(20) 年后两位(20)
               时(12) 分(02) 秒(19)   → 2020-04-04 12:02:19 周六（机器 RTC 未校准）
```
- `0x0007` 写寄存器里的“时间 / 当前曲目位置 / 播放状态 / EAX”是**分开的帧**：
  时间=`0x0110`（日历 RTC）、当前曲目位置=`0x0119`、播放状态=`0x010B`、EAX=`0x02xx`。
- `0x0008` 请求寄存器返回的是**这一批帧的合集**，其中“时间”= `0x0110` 日历时钟，
  **与“当前曲目已播多久/总时长”毫无关系**。播放计时另走命令 `0x0101`（elapsed）。
- 实时读数：elapsed=`0` 秒（0x0000）；current_track（队列位置）=`1`（0x0001）。

### ③ `0x000C` POSTID —— “曲目上是 TrackID，播放列表上是 PlaylistID”

- 这是**同一个帧号在两类数据库条目里的不同语义**（libnjb `protocol3.h:93`）：
  - 在**曲目库**（DB_TRACK）条目里，值是 32bit **TrackID**（歌曲唯一 ID）；
  - 在**播放清单库**（DB_PLAYLIST）条目里，值是 **PlaylistID**（清单唯一 ID）。
- 后面的“PlaylistID”就是**播放清单自己的数据库主键**——用于定位/重命名/删除/加成员
  （`0x0108 读成员`、`0x0001 改名`、`0x0005 删除`都以它为 entity_id）。它不是曲目 ID。
- 实机曲目 TrackID 样本：`0x0056E19F`=5693855、`0x005880C3`=5800131、`0x00485505`=4740357。
- 实机 PlaylistID 样本：`3594079`=0x36D75F / `3594041`=0x36D739 /
  `3616825`=0x373039 / `3616804`=0x373024（2进制见取数脚本）
  —— 与曲目 ID 同一量级但分属不同数据库命名空间，不可混用。

### ④ `0x0105` 时长 —— 【曲库元数据：曲目总时长（秒）】，不是播放态可读帧

- libnjb 头文件注释写 “String”，但代码 `protocol3.c:2226` 实为 `njb3_bytes_to_16bit()`
  读成 **16bit 秒数**，本侧 `list_tracks():668` 解析进 `track['length']`。
- 实机样本：第 1 首 `3600` 秒 = 0x0E10 = 60:00；第 2 首 `3652` = 60:52；
  第 3 首 `129` = 0x0081 = 2:09（标题 ' Legends Never Die'）。
- **它不是“当前正在播放曲目的剩余/总时长”可读命令**——播放接口无此能力（v23/v24 结论），
  只能全量扫曲库缓存。曲目总数实机 `0x12DE`=4830；专辑 `0x0125`=293；清单数 `0x000A`=10。

### ⑤ `0x010C` SEEKTRACK —— 【写命令】定位到当前曲目的毫秒位置（W）

- libnjb 标注 `32 bit word W: seek to position (in ms) in current track`，**W=只写**。
  本侧 `seek(pos_ms)` 用 `0x0007` 写帧 `01 0C <pos_ms:4大端>` 实现。
- 它**不是读取接口**，不能拿来“读当前播放位置”；已播位置只能读 `0x0101`（秒）。

### ⑥ `0x010F` 播放列表名 —— 已取，UCS2-BE 字符串

实机 10 个清单，前 4 个：`舒缓音乐`、`告示牌流行`、`欧美流行`、`杰克逊`
（各带 `playlistid`：3594079 / 3594041 / 3616825 / 3616804）。

### v25 软件改动

- **电池**：`get_battery()` 电量百分比改为直取 16bit 原始值（85→85%），修复 8% 错误。
- **进度条模拟**：上层播放控制框体不再模拟进度随时间空走。点“▶播放”直接放机器中队列、
  软件识别不到曲目对象/唱读时（`_current_track_identified()` 为 False），进度条**停止每秒
  +1 模拟**，只保留框体标题“当前播放位置 XX:XX”（来自设备 `0x0101` 真实回读），并仍按
  **30 秒**周期同步一次机器；识别到曲目（本地曲库对象）时保持原模拟推进。

`njb3_gui_editor.exe`（见 spec 的 `name=`），发布版永远提示“未找到”。已修正候选列表，
优先 `njb3_gui_editor.exe`，兼容源码副本 `源码_njb3_layout_editor.py`。

### 3. .ui 导入官方设计器显示错乱
根因：`NJB3完整界面.ui` 头部声明 `<interface version="1.3">`，布局却用旧版 1.0 的
`<pack><property...>` 标签。设计器 0.46.2 按 1.3 只认 `<layout manager="pack">`，
读不到就全部回退默认 grid、丢弃 fill/side/expand，控件堆叠错乱。已重写生成脚本
`build/gen_full_ui.py` 输出规范格式：
- `<layout manager="pack"><property name="fill">x</property>...</layout>`
- 设计器同款 `UIDefinition.load_file()` 实测：119 控件全部识别，88 处 pack 布局、31 处
  Column 默认 grid（正常），`top_bar`/`stage_tree` 的 fill/side 属性完整读回。
- Builder 实测构建成功，界面尺寸 1406×520（正常展开，不再堆叠）。

### 4. 关于“读取源代码改 UI / 让软件加载 .ui”
- tkinter 无反向工具：界面是 `ttk.Button(...).pack()` 命令式创建，没有可供设计器
  反向读取的界面描述；pygubu 只能 .ui→界面/代码，不能代码→设计器。
- 运行时加载 .ui 需重写约 750 行 UI 构建代码（50+ 事件绑定、动态分栏/拖拽/trace/
  列配置/隐藏自检强依赖控件 id），属高风险大改。经确认，本版先交付确定性修复，
  界面文件加载留待后续单独评估。现有“皮肤配色 + 布局编辑器”已覆盖常见外观调整。
